# Public email and password signup plan

2026-11-17 · Owner approved execution and implementation. The release gate below records the remaining production decisions and checks.

## Findings before implementation

- The existing `/signup` form accepts Email, Password, and Confirm Password, and `/register` redirects to it. Production uses Appwrite Auth. The restriction comes from the server-side `HFT_ALLOWED_ACCOUNT_EMAILS` setting. Frozen requirements specify three approved addresses, and the parser accepts up to four distinct valid addresses. Signup rejects other emails before creating an account. Login, session restoration, recovery initiation, password change, and trusted actor resolution also apply the allowlist. Removing the signup check alone would leave new users unable to use the app. [Runtime configuration](../../../src/infrastructure/appwrite/config.ts#L108) · [Account service](../../../src/infrastructure/appwrite/auth/account-service.server.ts#L82) · [Product actor](../../../src/infrastructure/appwrite/runtime/context.server.ts#L110)
- Signup creates an account with the keyless Appwrite Account client and then uses that same client for its session. The code reads `session.secret` for the `hft_session` cookie, while Appwrite documents that field as available only when the request uses an API key. Login already uses a server-key Account client to create its session. Verify the documented behavior in an isolated project and reuse the existing login session path if confirmed. A signup response should only report a session when the server can restore it using the issued cookie. [Signup and login implementation](../../../src/infrastructure/appwrite/auth/account-service.server.ts#L102) · [Appwrite Session model](https://appwrite.io/docs/references/cloud/models/session) · [Appwrite SSR login](https://appwrite.io/docs/products/auth/server-side-rendering)
- Appwrite can separately cap total project users and reject new registrations with `user_count_exceeded`. Live Console settings, Auth inventory, and current usage were outside this review. Verify the project cap, enabled Auth methods and email/password policies, verification and recovery delivery, and Free-plan headroom before rollout. [Appwrite response codes](https://appwrite.io/docs/apis/response-codes) · [Appwrite pricing](https://appwrite.io/pricing)
- Household creation already supports different users creating separate households. Joining an existing household requires the code, a join request, and leader approval. Production also enforces a four-active-member limit per household. Some create/join transaction checks scan across households, memberships, or requests under a bounded row reader. Test across multiple households and resolve any public-signup capacity blocker with scoped, indexed queries and preserved transaction guarantees. [Household commands](../../../src/infrastructure/appwrite/runtime/command-household.server.ts#L19) · [Member cap](../../../src/infrastructure/appwrite/runtime/command-context.server.ts#L43) · [Row reader](../../../src/infrastructure/appwrite/reads/tables.server.ts#L9)

## Approved requirement change

Any person who can confirm ownership of a valid email address can create their own account and sign in with email and password. Keep the existing signup fields and add a verification step for new accounts. Allow an unverified session to complete or resend verification and sign out. Require a verified Appwrite identity before establishing product access or creating a product Profile. Verification establishes control of the mailbox before an address becomes an active product identity. [Account requirements](../REQUIREMENTS.md#accounts-and-households) · [Appwrite verification](https://appwrite.io/docs/products/auth/verify-user)

- **Accounts and data.** Keep existing users' Auth IDs and Profile IDs, and keep membership, ownership, history, and passwords attached to those IDs. Inventory existing users' verification state before choosing the transition. If verification is needed, stage it in place with the current access policy still active and confirm every existing member can sign in before enforcing it at cutover. Resolve any account that cannot complete verification with the owner before switching policies. Review how prior sessions are handled after recovery of an unverified account so a recovered account remains under the mailbox owner's control. The existing Auth/Profile model is the starting point. No schema change is currently proposed.
- **Household and finances.** A new verified account starts without a membership and follows the existing Create or Join flow. The owner subsequently approved ten active members, including the leader, and ten pending requests per household. The limits apply at acceptance and request submission respectively. Account signup, login, and email verification operate independently. Preserve one active household per user, leader approval, household isolation, owner-private data, and exact poisha arithmetic. [Household access gate](../../../src/presentation/runtime/household-access-gate.client.tsx#L19)
- **Profile and screens.** Reuse Signup, Login, Forgot Password, and Reset Password, and add verification instructions, resend and expired-link states, and a route back into the existing onboarding. New profiles use the neutral `Member` default within the existing 1–20 character rule. This keeps email local parts out of other members' views and handles long addresses. Existing users keep their display names and can edit them from Profile. [Profile bootstrap](../../../src/infrastructure/appwrite/auth/account-service.server.ts) · [Profile rule](../REQUIREMENTS.md#accounts-and-households)
