## Outcome and scope

**M0 is complete: inspection and proposed mobile images only.** The main problem is desktop-sized framing and spacing stacked on a phone, which pushes useful information and actions far down the page. Horizontal fit and passing page-level accessibility checks did not establish a good mobile experience.

Open the [visual review gallery](mobile-design-2026-10-13/index.html) for six proposed image boards and current screenshots. The [measurement inventory](mobile-design-2026-10-13/measurements.json) contains 146 page/state/viewport captures; the [generation prompts](mobile-design-2026-10-13/PROMPTS.md) retain the built-in imagegen prompts and corrections. The six boards contain 27 illustrative page/state compositions. They are references for review, not an implemented or approved redesign.

No application source, shared/desktop stylesheet, dependency, provider configuration, schema, production record, stored file or deployment was changed. All browser data was synthetic, isolated in disposable Playwright contexts. No production account was used. The local source was the released design with a clean application working tree at entry, HEAD `0ae12b1b719d7ec8639ee668f0f1f1a93ea4bec3`.

## Evidence and limits

- Chromium: 17 route views at 320, 390, 430, 640, 768 and 1440 CSS-pixel widths, each with an 844px viewport height. This includes every principal product page, four auth pages, Credits and a missing route.
- Firefox and WebKit: the eleven principal product views at 390 × 844. They use the same local composition and synthetic records; these are browser-engine checks, not physical iPhone/Android tests.
- Additional Chromium evidence: More, notification popup, Add Card, landscape Card dialog (844 × 390), Rename, receiver confirmation, filled Expense form, Date picker, Percentage split, reduced-height form (390 × 430), Household Member/Pending/no-household/Create/Join, empty month, no-match search, validation, financial lock and runtime-data recovery. Notification semantics were checked at both 390 and 1440.
- 146 measured views, 292 screenshots, no positive page-level horizontal overflow, and no page errors in the three core inventory runs. Internal category/chart scrolling is permitted and is not treated as page overflow.
- All 17 primary Chromium route views had zero captured Axe violations at 390. State inspection additionally found the notification-menu failures and Date-picker contrast failure below. This is not a blanket WCAG certification or proof of good UX.
- Static captures use reduced motion and wait for finite animation completion and fonts. Money fixtures use **13 September 2026** as browser time, with August expenses, rather than pretending the samples are live October balances.
- Local Profile lacks the production password form; that form and production recovery/session states were reviewed from source and existing release evidence, not freshly exercised against Appwrite. `/` and `/register` aliases, root/global errors, deleted/legacy/former-member variants and production transport-outage states received source review rather than new complete browser journeys here.
- Real virtual-keyboard behavior, Safari input-focus zoom, device safe-area cutouts, OS back gestures, screen-reader behavior, poor mobile networks and real user task completion remain unmeasured. Reduced viewport height is only a layout proxy for a keyboard. No usability interviews or actual user complaint details were available.

### Image limitations that must not become product changes

The written requirements and existing source override illustrative details in generated images. Corrections removed misleading Pending status, an invented Card-name maximum, conflicting unread/empty notification copy and an unsupported first-ever-month assertion. Remaining differences must be resolved at implementation, not copied blindly:

- The category pictures are illustrative glyphs; retain the actual 12 category PNG assets, canonical order, tooltips and internally scrolling strip. No category filter is authorized.
- Keep the literal existing **Spent** label, payer read-only with no selector, field validation, actual card designs/demo constants and exact Poisha-derived values. Graph shapes, timestamps, history rows and sample records in the concepts are fictional and not reconciliation evidence.
- Member Household must not show member-management actions; incidental generated overflow glyphs confer no authority. Leader actions must retain current gates and confirmations. Preserve leader-first ordering and proper current-viewer identity. Only More is the active bottom destination for Cards/Household/Profile; incidental extra selected icons in the board are not intended.
- House codes always contain exactly nine digits, preserving leading zeroes. The Create image's shortened preview text is not a valid example and must not be copied; the authoritative sample is `000000222`. No new preview feature or invite action is approved.
- Credits remains standalone using every actual author and source URL from the existing asset register. Generated icon names/authors and the illustrated bottom bar are not attribution or navigation authority.
- Allowlisted self-signup is not a manual account-review process; use existing auth copy. Preserve password rules, error/reset/token handling and real success-state conditions. No private allowlist or reset token is displayed.
- Keep all content beyond the visible composition: especially Dashboard analytics, Monthly Report settlement summary, original-amount/current-balance warning states, historical receipt states, privacy instructions and role-specific blockers. A compact layout does not authorize deleting a module or confirmation.
- A confirmation opens from its existing owning flow; the generated background is merely illustrative. Preserve dialogs' focus restoration and pending-operation dismissal rules.

### What needs design acceptance

Spacing, wrapping, mobile font sizes, readable enabled dates and effective touch areas are presentation corrections consistent with existing rules. A Filters sheet, long-form dialog sheet, revised action-footer arrangement or material mobile module restructuring should be accepted as a concrete mobile presentation amendment before implementation. All filters must remain live; no Apply/draft-filter behavior is proposed. Visible navigation labels would additionally supersede the explicit icon-only requirement and are not part of these images.

## Desktop-preservation and next-phase gates

M0 authorizes no implementation. Recommended sequential scope, after owner acceptance:

1. **M1 — Mobile shell and spacing:** cap phone overrides below 640px; explicitly review 640–767 large-mobile behavior rather than changing the full tablet range by accident. Preserve the existing desktop switch at 1024px and all tablet navigation. Compare fixed-data 1024/1280/1440/1920 screenshots and geometry before/after.
2. **M2 — Expense list/form/detail:** implement the accepted live Filters presentation, metadata wrapping, compact form and touch fixes with the same mounted form/handlers/command IDs. Verify exact equal/amount/percentage values, drafts, errors, privacy, financial locks and receipt lifecycle.
3. **M3 — Remaining pages/states:** compact Report/Household/Profile/auth and accepted dialogs. Treat shared notification/date accessibility defects as explicit scope with desktop visual parity checks.
4. **M4 — Acceptance:** Chromium/Firefox/WebKit at 320/360/390/430 and mobile boundary widths, landscape and reduced height; serious/critical Axe on opened overlays as well as pages; mobile touch/scroll/keyboard and real-device safe-area testing; no positive page overflow; exact money text and existing permissions unchanged. Verify desktop geometry and zero pixel differences under stable fixtures, or review any rendering-only noise explicitly. Deployment remains a separately authorized code-only step.

Do not change global tokens, desktop component defaults or desktop shared grid tracks merely to fix phones. Use scoped media queries and mobile variants; keep one mounted form rather than duplicate hidden form trees. No financial/domain/application/persistence/API/provider/session/asset-license change, dependency, new feature, paid service or migration is part of the mobile proposal.
